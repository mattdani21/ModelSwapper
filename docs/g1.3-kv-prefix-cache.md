# G1.3 lever: cross-turn KV prefix cache for retry phases (issue #16)

Status: IMPLEMENTED + MEASURED (local 4B stack, 2026-08-24). Branch
`wt/g1.3-kv-cache`. Review card: created on completion.

## What

FreeToken-style cross-turn KV prefix caching for the CODE phase retry loop.
The code prompt is `task + starter + plan + feedback + instruction`; the
first three are byte-identical across retries — only the bounded critic
feedback changes. Instead of re-prefilling ~2.5K tokens on every retry, the
pipeline checkpoints the llama-server slot state after the first code attempt
(`POST /slots/0?action=save`, ~650 MB at 8192 ctx, ~100-400 ms) and restores
it on each retry (`action=restore`, ~30-100 ms). llama-server's longest-
common-prefix logic then re-prefills only the feedback suffix (FreeToken:
"re-prefill only the suffix after an edit").

Correctness first: any restore failure falls back to a full prefill. The
cache is per `(model, task, plan)` — the checkpoint filename is a SHA-256 of
model path + file size + task id + problem + starter + plan.

## Mechanism notes (llama.cpp b10270)

- The old `POST /slots/{id}/save?filename=` shape is gone; this build wants
  `POST /slots/0?action=save|restore` with `{"filename": ...}` in the body.
- The server must run with `--slot-save-path <dir>` and `-np 1`. With the
  auto default (`-np 4` + unified KV) the completion lands on an unpredictable
  slot and each slot gets n_ctx/4, which makes save/restore hit an empty slot.
  `runtime/swap_runner.py` now defaults to `-np 1` (env-overridable via
  `LLAMA_NPARALLEL`) — strictly sequential pipeline, one honest slot.
- Saving *after* generation (slot = prefix + generated tail) is fine: the
  restore + next prompt truncates to the longest common prefix automatically.

## Measurement (local 4B stack: Qwen3-4B-Q4_K_M code/reason, Qwen3-0.6B-Q8_0
review, ctx 8192, temp 0.2, max_tokens 2048, max_iterations 3)

9-task subset (bugfix 01/02/03/07/13, feature 04/12, refactor 05/12), same
tasks both modes, only `--kv-cache-dir` differs. Baseline ran first.

| Metric | Baseline | Cached | Δ |
|---|---|---|---|
| Retry-phase prefill time (7 retry phases) | 63,731 ms | 5,200 ms | **−91.8%** |
| Retry-phase prompt tokens | 18,294 | 1,320 | −92.8% |
| Restore hits / misses | — | 7 / 0 | — |
| Slot saves | — | 9 / 9 | — |
| Paired tasks only (bugfix-13, refactor-12; 2 retries each in BOTH modes) | 35,628 ms | 2,637 ms | **−92.6%** |
| Pass rate | 7/9 | 6/9 | see note |
| Wall clock | 2,207 s | 2,271 s | generation-dominated; see note |

Per retry phase the cost drops from 8.5–9.9 s (2.5–2.8K tokens) to
0.6–1.0 s (150–260 tokens) — the ≥ 50% acceptance bar is met with margin.

Pass-rate note: the cached run lost bugfix-03, which failed on its FIRST
attempt. The KV cache is inert on attempt 1 (identical code path; the slot
save happens after generation), so this is sampler noise (temp 0.2, random
seed), not a cache regression. Attempt-1 outputs are unchanged by the cache
by construction.

Wall-clock note: total wall is dominated by generation (~2K tokens/attempt at
~25-40 tok/s on M3 Metal). The cache removes prefill time (retry prefill was
2.9% of baseline wall on this subset), and the run-to-run outcome differences
(retry storms are stochastic) swamp that saving in the wall totals.

## G1.3 projection at 27B scale (from committed overlap full-50 run)

Retry-phase prefill at 27B (overlap, 8192 ctx, full 50-task suite) was 10.5 s
of 2,042 s wall — **0.51% of wall**; total prefill (all phases) was 2.3%.
Applying the measured 91.8% retry-prefill reduction: 2.12× → **2.11×** (upper
bound with retry prefill fully eliminated: 2.109×). The lever cannot close
2.12× → <2× at this operating point — generation and retry storms dominate,
not prefill. Recorded as data per issue #16's stop condition ("missing a
target is data, not failure"). G1.3 remains open; the honest next levers are
retry-storm reduction and native-arch builds (documented hypotheses in
docs/parity-report-phase1.md Addendum 3).
